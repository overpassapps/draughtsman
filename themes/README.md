# Themes

Draughtsman has two separate theme layers, because "skin the app" and "style my diagrams" are different problems with different owners (spec section 8).

| Layer | What it controls | Who sets it | Where it lives |
| --- | --- | --- | --- |
| Chrome theme | App shell: toolbars, panels, buttons, logo, login page, favicon, product name | Instance admin | `themes/chrome.yaml`, plus runtime overrides under the data folder's `branding/` |
| Diagram theme | Default node/edge styles per `kind`, palette, fonts, grid, canvas and export backgrounds | Workspace admin, overridable per document | `themes/diagram-*.yaml`, and the `themes` table once storage lands |

## Files in this folder

- `chrome.yaml` — the shipped Overpass default chrome theme, in the shape given in the spec (`logo:`, the compact marks and `favicon:` are all optional). It names none of them: until an organisation supplies a logo, product name or favicon, the web app shows the Draughtsman mark and favicon it ships in `web/public` (the shell header, the sign-in and first-run pages, and the favicon; the About page always shows the lockup, apart from the organisation's own block). Brand hex values were confirmed on 21 Sep 2026 (spec section 13).
- `chrome-example-client.yaml` — a deliberately fictional second chrome theme (product `Northwind`, green palette, serif font, light mode) proving a second theme loads. It is not the build-time default; select it with `theme.chrome` in `draughtsman.yaml` (below).
- `assets/` — the logo and favicon SVGs a chrome theme may name (only the Northwind theme does; the shipped default names none). The Overpass wordmark files are kept for a theme that wants them: the white `overpass-logo-light.svg` reads on a navy header, while the red `overpass-logo.svg` is for a light background. `logoCompact:` / `logoCompactLight:` name an optional header-only variant (`overpass-logo-compact.svg`, `-compact-light.svg`, derived from the wordmark with the bridge strokes thickened, the letters enlarged and the "apps" line dropped, because the hairlines vanish at 24 to 32 px); a theme that names none, or an instance whose admin uploaded a logo, draws its normal logo in the header. Its favicon is the bridge symbol lifted from that artwork into a square tile, because a wordmark is unreadable at tab-icon size. The Northwind compass is fictional.
- `diagram-overpass.yaml` — shipped default diagram theme: red accents on dark navy for architecture work, white paper for export.
- `diagram-neutral.yaml` — Lucidchart-like blues and greys.
- `diagram-mono.yaml` — black on white for documentation.

## How the tokens are used

- All colours, radii, fonts and spacing become CSS custom properties. In development they are compiled from the YAML by `web/scripts/build-tokens.ts`, which runs before every `npm run dev`, `build`, `lint` and `test` in `web/` and writes `web/src/generated/tokens.css` (git-ignored) and `web/src/generated/diagram-themes.ts` (the diagram themes as typed data). In a running instance the server compiles the configured chrome theme at startup and serves it at `GET /api/theme/chrome.css`, and the SPA injects those tokens over the build-time ones (`web/src/theme/chromeTheme.ts`), so an admin can change the chrome theme without rebuilding. No component references a literal colour; the app shell uses `var(--chrome-*)` and the canvas resolves node and edge styles from the compiled diagram theme.
- Every chrome token has light and dark values. In `chrome.yaml`, `colors` is the set for the theme's `mode` (dark when `mode` is `system`), and a `light:` or `dark:` block carries the companion mode; a missing block falls back to `colors`. The compiler emits `:root` for the chosen mode, `:root[data-theme-mode="dark"]` and `:root[data-theme-mode="light"]` for an explicit switch, and a `prefers-color-scheme` rule when `mode` is `system`. Token names are kebab-cased: `surfaceRaised` becomes `--chrome-surface-raised`.
- A diagram theme maps each node `kind` to a default fill, stroke, stroke width, text colour, font and dash, and each edge `kind` to a stroke, width, dash and arrowheads. Both `nodes` and `edges` carry a `default` entry used for kinds the theme does not name (unknown kinds are allowed; lint flags them). Fields a kind omits inherit from `default`.
- **Two surfaces, one theme.** The renderer takes a `surface` (`web/src/canvas/DiagramSvg.tsx`): on screen it paints `canvasBackground` behind the drawing and under edge labels; export re-renders the same document with `surface="export"` and paints `exportBackground`. Fills, strokes and fonts are identical on both, so every stroke in a theme must be legible on both backgrounds. Text drawn on a node's fill keeps its kind's `textColor`; text drawn straight on the surface (edge labels, and transparent-fill nodes such as `text` and `image` that sit on the surface rather than inside a container) takes the surface's own text colour, the optional `canvasText` and `exportText` tokens. When a theme omits them the colour is derived from the surface background's luminance: light text on a dark surface, dark text on a light one (`surfaceTextColor` in `web/src/theme/resolveStyle.ts`). Deriving it needs a background the renderer can read, so `canvasBackground` and `exportBackground` are hex, `#` included; anything else and surface-borne text keeps the theme's own colour rather than a guess, which the compiler warns about. A colour the document gave that text keeps it, and the two ways of giving one are read differently on purpose: an element's own `style.textColor` counts by presence, since naming even the kind's own colour is deliberate, while a `theme` override counts only where it differs from the workspace theme, so a mistyped `token:` name that changed nothing leaves the surface to keep the label legible. The grid belongs to the editor, so export paints the drawing on bare paper. SVG and PNG exports are one drawing and both carry that paper as an opaque background rectangle (no transparent option). A kind whose fill equals `canvasBackground` looks see-through on screen but exports as a slab, so a grouping kind such as `container` takes `fill: transparent` instead. The shipped `overpass` theme is dark navy on screen and white paper on export, which is why its greys are mid-tones rather than near-white.
- **Documents store only deviations.** A node with no `style` renders from the theme plus its kind's default, so switching a document's diagram theme restyles it instantly and re-skinning is a no-op on the document. A document's optional `theme` map overrides theme tokens by dotted path (`nodes.service.fill`, `edges.flow.stroke`, `palette.red`, `grid.color`, `canvasBackground`); a path must name a single token, so one that stops on a group of them (`nodes.default`), or on the theme's own identity fields (`name`, `description`), is ignored like any unknown path. A colour-valued override may name a palette entry as `token:<name>`, exactly as an element style may, and an unknown name leaves the token as the theme had it; a `palette.<name>` override is itself a colour literal, never a reference, so the order a document lists its keys in cannot change the picture. An element's own sparse style still wins over those. See `web/src/theme/resolveStyle.ts`.
- **Export uses the document's diagram theme, never the chrome theme.** A red-and-black app still produces a white-paper PDF for a client deck.

## Overriding as a client

Drop your own chrome theme YAML (and its logo and favicon) into a `themes/` folder inside the instance's data folder (`./data` by default, or `DRAUGHTSMAN_DATA`) and point `theme.chrome` in `draughtsman.yaml` at it, then restart:

```yaml
theme:
  chrome: my-theme.yaml        # resolved against <data folder>/themes/, then <data folder>, then the shipped themes
```

The server loads that file at startup, compiles it to `--chrome-*` custom properties and serves them with the product name, logo, favicon and mode; the browser picks them up on the next load. A missing or invalid file logs a warning and falls back to the shipped Overpass theme, so a bad theme never stops the instance starting. Nothing else changes: the product name, logo and colours are all config. The Draughtsman mark is only ever the default: once a theme or the Branding page sets a logo or a product name, that is all the shell and the sign-in pages draw, and the mark appears only in the About screen's own product block. Themes are plain files so they can be version-controlled and shipped by an IT team's configuration management.

An admin can also change the **product name**, **logo**, an optional **light-on-dark logo** and the **favicon** at runtime from the web admin page `/admin/branding`, without file access to the server and without a restart (M3; the API is in `docs/api.md#branding`). Those are stored in the data folder's `branding/` directory and layered over the theme file, which stays the fallback: removing an override, or "Reset all branding", returns to what this file says. Colours and the other tokens stay the theme file's, so a full re-skin is still a YAML edit. A `logoLight:` field may also be named in the YAML itself; it is the variant drawn on a dark surface, falling back to `logo:` when absent, and the dark shipped theme relies on the fallback because its `logo:` is already the white wordmark. An uploaded SVG is validated against a strict allowlist before it is stored and served as an image with a restrictive Content-Security-Policy, so a logo file can never run script in the app's origin.

To see a second theme load without writing one, set `theme.chrome: chrome-example-client.yaml` (shipped with the server) and restart.

An admin can also create **organisation themes** without touching files, at `/admin/themes` (docs/api.md `## Themes`): a chrome theme (colours, radius, fonts, dark and light sets) and a diagram override, with live previews and the contrast warnings below, stored as `themes/org/<id>.yaml` in the data folder. The default one replaces this file's colours for every user; the logo, favicon and product name stay branding. Theme files export and import from the page in this same YAML shape plus a `diagram:` block, which the chrome loader ignores, so a theme exported from the page also works here as a `theme.chrome` file.

Per-user or per-workspace themes are phase 2; the MVP is one default theme per instance.

## Validation

The token compiler checks contrast ratios against WCAG AA for the chrome tokens (text on surface, brandText on brand, and so on), for each filled node kind's text on its fill, for the surface text colour (edge labels and transparent-fill nodes) on each of the canvas and export backgrounds, and for each node and edge stroke on both backgrounds. It never compares a node kind's fill with a surface background, and skips the stroke check when a kind's stroke equals its fill (`sticky` in `overpass`), so a clean run means every pair it checks passes, not that every shape reads on both surfaces. It **prints warnings and never fails the build**. A theme with poor contrast is a support conversation, not an outage. Every shipped theme now compiles with no warnings. The `neutral` diagram theme's container, lane, external and note strokes were darkened to clear 3:1 on white (QA-03). In the chrome, `border` stays a deliberate hairline for dividers and panel edges (decorative lines are outside WCAG 1.4.11), while the outline of a control (input, select, button, swatch) is `--chrome-border-strong`, derived in `app.css` as 52% of `text` over `surface` and checked at 3:1 against `surface` and `surfaceRaised` (`web/src/theme/themeContrast.ts`). It is derived rather than a token, so a client theme needs to supply nothing and still gets a readable outline.
