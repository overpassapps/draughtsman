# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

## What this is

Draughtsman: self-hosted, agent-native diagramming. The model (a typed graph) is the truth; the picture is a render. Source of truth is `docs/spec/build-spec-v0.1.md`, including its `## Amendments` section. Read it before changing anything of substance.

## Layout

- `Draughtsman.sln` at the root; `src/Draughtsman.Core` (model, kind vocabularies, `IStore`, the DSL parser and printer under `Text/`, and `DocumentSchema` - the embedded `document.schema.json` loader and validator every validating caller shares, with `SchemaValidator` doing the checking in-house), `src/Draughtsman.Sidecar` (`ISidecarClient`: spawns and supervises the Node sidecar), `src/Draughtsman.Storage` (EF Core `IStore` with SQLite and Postgres contexts and their migrations), `src/Draughtsman.Mcp` (the MCP tools: `list_documents`/`read_document`/`create_document`/`patch_document`/`render_document`/`diff_documents`/`critique_document`/`get_schema`, transport-agnostic over `IStore`/`ISidecarClient`), `src/Draughtsman.Server` (ASP.NET Core minimal API hosting the document REST contract, `docs/api.md`, plus the MCP tools over streamable HTTP at `/mcp` and, via `draughtsman mcp --stdio`, stdio), `tests/*` (xUnit).
- `web/` is the Vite + React 18 + TypeScript SPA; the server serves `web/dist` when it exists. Diagram export (File menu and palette `Export PNG`/`Export SVG`) is client-side only (`web/src/editor/exportDiagram.tsx`): it re-renders `DiagramSvg` on `surface="export"` through `react-dom/server`, cropped to `DocumentIndex.contentBounds`, so it never reads the virtualised on-screen SVG. Orthogonal connectors are routed in-process by `canvas/routeDocument.ts` (the canvas's own `routingSnapshot` + `handleRouteBatch`), never left to the stored waypoints, so an export and the editor draw the same paths; the sidecar's `route.document` bundles that same module for the server (see the MCP bullet below), so there is one router, not a copy per renderer. PDF is unbuilt: a client-side PDF would take a library, and the server's optional headless-Chromium `ExportConfig.Chromium` is not wired up.
- `sidecar/` is the Node sidecar (ADR 0002): ELK layout and Yjs materialisation over stdio JSON-RPC. Protocol, methods, layout semantics and the Yjs document shape are in `sidecar/README.md`.
- `src/Draughtsman.Core/Import/` holds text importers (Mermaid flowchart and `sequenceDiagram`; `Drawio/`, `Visio/` and `Sql/` have their own bullets below) and `MermaidExporter`, their mirror (`POST /api/export/mermaid`, MCP `read_document format=mermaid`, File > Export Mermaid: a shape or arrowhead Mermaid cannot spell degrades with a `%%` comment, never an error; when sequence fragments and notes enter the model, its sequence writer is where they go); `POST /api/import/dsl` is not one of them, only `Dsl.Parse` behind the same `{ document, warnings }` envelope. Both endpoints are documented in `docs/api.md`, which is where every HTTP endpoint gets documented.
- `docs/adr/` holds the decisions later work depends on: 0001 runtime and release targets, 0002 CRDT materialisation and layout engine (Node sidecar over stdio JSON-RPC), 0003 storage providers (SQLite default, Postgres MVP, SQL Server phase 2).
- `themes/` holds the chrome and diagram token files; `design/atlas/` holds per-screen design notes.
- `Dockerfile` and `docker/` build the release image (build-spec-v0.1.md's deployment table, M3): multi-stage (sidecar and web built by their own Node stages, then a framework-dependent `dotnet publish`, no `-r`, onto `mcr.microsoft.com/dotnet/aspnet:10.0` with Node 22 added for the sidecar child process), non-root fixed uid `10001`, `DRAUGHTSMAN_DATA=/data` for the volume mount. `ASPNETCORE_URLS=http://0.0.0.0:5180` is the existing override `Program.cs` already checks first, so the container binds every interface without touching `ServerConfig.Host`'s loopback default. `--build-arg INSTALL_CHROMIUM=true` installs Playwright's Chromium via the npm `playwright` package at the same version as the `Microsoft.Playwright` NuGet reference (the runtime image has no .NET SDK, so `dotnet tool install` cannot run there); `docker/entrypoint.sh` then seeds `export.chromium.enabled: true` into a data folder that has no `draughtsman.yaml` yet, never overwriting one already saved. README's Docker section has the build/run commands and the buildx release command (not run by CI or this repo).

## Build and test

- Backend: `dotnet build` then `dotnet test` from the root. Warnings are errors (`Directory.Build.props`); SDK pinned by `global.json`. `dotnet build` needs Node 22 on PATH: `Draughtsman.Sidecar.csproj` runs `npm ci` and bundles `sidecar/dist/sidecar.js`, then copies it into every referencing project's output as `sidecar/` (`-p:BuildSidecar=false` to skip, `-p:NodeExe=` to point at a Node). The Sidecar and Server tests spawn that real bundle.
- Storage provider suite: `tests/Draughtsman.Storage.Tests/StoreContractTests.cs` is the specification of `IStore`; every provider subclass runs it unchanged. SQLite always runs; Postgres runs against `DRAUGHTSMAN_TEST_POSTGRES` (CI's Ubuntu service container, or the local `docker run` in `docs/api.md`) and skips otherwise. A provider that cannot pass a test is a provider bug, not a test to special-case.
- Migrations: regenerate per provider with the `dotnet ef` commands in `src/Draughtsman.Storage/Design/DesignTimeFactories.cs` (tool pinned in `.config/dotnet-tools.json`, `dotnet tool restore`). They apply at startup; SQLite is copied to `data.db.pre-migration-<stamp>` first.
- Optimised-JIT faults hide at tier 0: a .NET 10 JIT on **x64** (Linux and Windows; arm64 is fine) miscompiled `SqliteTableCounts.ReadVerified`'s old shape (a call's result left on the IL stack while `string.Equals(outLocal, "ok")` read an `out` local the call had not yet filled), so every verified copy "failed" with `integrity_check reported: ok`. It shows only in optimised code (tier 0 is correct, a once-per-start call in production runs at tier 0), so CI failed it only after earlier tests had called the method 30 times. `Draughtsman.Storage.Tests` therefore sets `TieredCompilation` false (optimised from the first call), and the integrity text now travels in the result (`SqliteTableCounts.IsWhole`), never an `out`. To reproduce an x64-only failure from an arm64 Mac: `docker run --platform linux/amd64` under qemu with `DOTNET_EnableWriteXorExecute=0` (build with the native arm64 SDK, run `--no-build` under amd64; a pull for another platform RETAGS the shared image name, so tag your own copy and never clobber the arm64 tag), or on a Windows-on-ARM machine install an x64 SDK beside the arm64 one (`dotnet-install.ps1 -Architecture x64`) and set `DOTNET_TieredCompilation=0`. `DOTNET_JitDisasm=<Method>` plus `DOTNET_JitStdOutFile` prints the generated code in a release runtime.
- Frontend: `cd web && npm ci && npm run lint && npm run build && npm test`. Node 22.12 or later. Each of those scripts first runs `npm run tokens` (`web/scripts/build-tokens.ts`, executed with Node's type stripping), which compiles `themes/*.yaml` into the git-ignored `web/src/generated/` files; nothing in `web/src` compiles without them.
- Sidecar: `cd sidecar && npm ci && npm test` (builds first, then Vitest).
- Run: `dotnet run --project src/Draughtsman.Server`, health at `http://localhost:5180/api/health`. `launchSettings.json` pins `ASPNETCORE_URLS` to 5180 and beats the environment, so a server on another port (parallel checkouts each need one) needs `--no-launch-profile`; confirm with `lsof` which process owns the port before driving it. `dotnet run -- mcp --stdio` needs `--no-launch-profile` too (the launch profile makes `dotnet run` print to stdout, corrupting JSON-RPC). Config comes from `draughtsman.yaml` in the data folder (`./data` or `DRAUGHTSMAN_DATA`); every key has a default (`src/Draughtsman.Server/Configuration/DraughtsmanConfig.cs`).
- Run `scripts/verify-local.sh` before landing any change: it runs the full macOS CI leg (dotnet restore/build/test/format, then web and sidecar lint/build/test) on your Mac, printing a PASS/FAIL line per step and keeping full logs in a temp directory. CI (`.github/workflows/ci.yml`) now runs only the Ubuntu and Windows legs, on pushes to `main` and `workflow_dispatch` (no longer on every pull request), to keep Actions minutes down; the `release-gate` job is still the single required check. The macOS leg is verified locally instead.

## Rules that are not obvious from the code

- The document model exists in four places that must change together: `src/Draughtsman.Core/Models`, `docs/schema/document.schema.json`, `web/src/model/types.ts` and `sidecar/src/model/types.ts` (whose field-by-field enumeration in `sidecar/src/yjs/shape.ts` must change with it). Both test suites validate `docs/examples/order-service.json` against the schema; extend the example when you add a field, and regenerate `docs/examples/order-service.dsl` with `Dsl.Print` (the golden test requires it byte-identical).
- The DSL (`docs/spec/dsl.md`, grammar in `docs/spec/dsl.grammar`) is the public API `Dsl.Parse` / `Dsl.Print` in namespace `Draughtsman.Core.Text`, not `.Dsl`: a namespace named after its own class shadows it for every caller under `Draughtsman.Core`. Any change to the model or the format must keep `DslRoundTripFuzzTests` green; run it longer with `DRAUGHTSMAN_FUZZ_ITERATIONS=30000`.
- `Node.Geometry` is null for a node whose source gave it no position: every node from a Mermaid import, and any node written without `@ x,y` in the DSL. Code that reads geometry must handle null; canvas fallback behaviour is documented in `design/atlas/editor-shell.md`. Geometry is absolute even inside a container, so moving a container does not move its children by itself: use `web/src/model/containers.ts` (move with contents, fit to contents, reparent, drop target). Editor commands over it: `web/src/model/grouping.ts` (group, ungroup, fit; padding is two theme grid steps; a crossed parent grows one level, never further) and `web/src/canvas/containerDrag.ts` (waypoints that travel with a drag, drop-into/out-of on release).
- Schema validation (`DocumentSchema.Validate`, implemented by `src/Draughtsman.Core/Serialization/SchemaValidator.cs`; ADR `docs/adr/0004-document-schema-validator.md`) is in-house and implements exactly the keywords `docs/schema/document.schema.json` uses; `SchemaValidator.Compile` refuses any other keyword, so adding one to the schema means implementing it there, with corpus and suite cases, in the same change. Its output (the verdict and the `location: message` lines, their wording and order, which the document API's `errors` and the MCP error carry) is a contract pinned by `tests/Draughtsman.Core.Tests/SchemaCorpus/` (10,446 texts recorded from the JsonSchema.Net it replaced: `expectations.jsonl` is never edited by hand and `intentional-differences.jsonl` is the whole list of deliberate departures, each a place the library threw) and by the official JSON-Schema-Test-Suite files in `JsonSchemaTestSuite/`. JsonSchema.Net, Json.More.Net and JsonPointer.Net are under the Open Source Maintenance Fee EULA (a fee for redistributing the binary), so no schema library may be added: `scripts/generate-notices.mjs` stops the run if one returns. Kept as it was: only the first of two duplicate member names is validated, and the deserialiser keeps the last (ADR 0004 follow-ups).
- Kind vocabularies are the JSON files in `src/Draughtsman.Core/Schemas/`, embedded in the assembly and loaded at runtime via `KindVocabulary`. Theme files map the same kind names; keep them aligned.
- Theme tokens: no component names a literal colour. A kind whose fill equals `canvasBackground` reads as see-through on screen but exports as a slab on the white paper, so grouping kinds (`container`) take `fill: transparent`; SVG and PNG export both paint `exportBackground` as an opaque rectangle (`editor/exportDiagram.tsx`). The chrome uses `var(--chrome-*)`; the canvas resolves styles from the compiled diagram themes (`web/src/theme/resolveStyle.ts`: theme kind default, then the document's dotted-path `theme` overrides, then the element's sparse style). `themes/README.md` documents the YAML shape and the compiler's outputs. The chrome theme is loaded at runtime, not only at build time: `theme.chrome` in `draughtsman.yaml` names a YAML file resolved against the data folder's `themes/`, then the data folder, then the themes embedded in the server assembly (shipped Overpass default plus the fictional `chrome-example-client.yaml`); `ChromeThemeLoader`/`ChromeThemeCss` under `src/Draughtsman.Server/Theming/` compile it and `GET /api/theme` (manifest) and `GET /api/theme/chrome.css` serve it, the SPA injecting it over the build-time tokens in `web/src/theme/chromeTheme.ts`. A missing or invalid file warns and falls back to the shipped default; both shipped themes and their `themes/assets/*` are embedded in `Draughtsman.Server.csproj`.
- Instance branding (M3): the chrome theme file is the fallback; an admin can override the product name, logo, `logoLight` and favicon at `/admin/branding` (`POST/PUT/DELETE /api/admin/branding*`, all `CookieAdminOnly`), stored under `<data>/branding/` and layered over the theme by the `ChromeBrandingService` singleton, which the theme endpoints read as a live snapshot, so a change lands with no restart - the compiled CSS (colours/tokens) stays theme-only. An uploaded SVG goes through `SvgSanitiser` in `Draughtsman.Core.Media` (strict element allowlist; rejects script, `foreignObject`, `on*`, external `href`, DTD/PI and CSS `javascript:`/`expression`/external `url(...)`) and is served as an image with `AssetEndpoints.SvgContentSecurityPolicy`; type/size/dimension rules live in `BrandingImages` (PNG/SVG logo, PNG/SVG/ICO favicon, 512 KiB, 4096 px / 256 px favicon). Branding changes are logged under `Draughtsman.Server.Branding`, not written to the document-scoped `audit` table (docs/api.md `## Branding`).
- Canvas (`web/src/canvas/`): `DiagramSvg` is a pure render of (document, theme, viewport, size) with one `<g data-id>` per node and edge, virtualised by `virtualise.ts`; `DiagramCanvas` owns pan and zoom. Keep culling and viewport maths as pure functions so they stay unit-testable. `DiagramSvg.test.tsx` snapshots the example document's SVG; update the snapshot deliberately when the render changes. The checklist item 29 benchmark (`docs/examples/perf-2000n-2500e.json`, 2,000 nodes/2,500 edges) is generated deterministically by `web/scripts/generate-benchmark.ts` (`npm run benchmark --prefix web`) and exercised by `DiagramSvg.perf.test.tsx`, which reports the numbers and fails only on a gross regression rather than the 16.7 ms frame budget. A pan or zoom frame must reconcile no element: `DiagramSvg` memoises its node/edge tree on everything but the viewport and reuses the visible set while it still covers the view (`visibleSetMemo`'s hysteresis; pinned by `DiagramSvg.reconcile.test.tsx`), so never feed a per-frame viewport value into element props. The only zoom-dependent rules are in `virtualise.ts`: `labelsLegible` (labels below 6 device px are not mounted on the canvas) and `fullDetail` (below 25% zoom nodes draw as plain world-space boxes and edges as plain lines with no markers or dashes, keeping their `<g data-id>` and hit stroke); export always draws full detail. jsdom has no layout or paint, so browser frame times need a real Chrome run. But when the visible set *does* change (a pan or zoom that crosses the hysteresis region, or a LOD threshold), `drawn` rebuilds a fresh element for every currently-visible node and edge, not only the ones entering or leaving - so `NodeView` and `EdgeView` are both `memo`-wrapped to bail on the ones whose props didn't actually change (checklist item 29 perf fix). `EdgeView` needs a custom comparator (`edgeViewPropsEqual`, unexported - a named export here trips `react-refresh/only-export-components`) because `labelAt` is a fresh `{x, y}` object from `placeLabels` on every rebuild even when a label hasn't moved; default reference equality would defeat the memo for any labelled edge. `NodeView`'s own body is split into an exported `NodeViewInner` plus `NodeView = memo(NodeViewInner)`, because `DiagramSvg.reconcile.test.tsx`'s render-count spy can't call an exotic memo component as a plain function - it wraps `NodeViewInner` in its own `memo()` instead, so mocking the module can't observe whether *this file* still applies `memo()`; that structural fact is pinned separately in `NodeView.test.tsx`/`EdgeView.test.tsx` by asserting `$$typeof === Symbol.for('react.memo')` (and, for `EdgeView`, that `.compare` isn't the default `null`). Real-Chrome frame-time measurement is unreliable through the browser-extension tab (`document.visibilityState` reports `hidden`, so `requestAnimationFrame` never fires there); use a headed Chrome launched via the global `playwright-core` install with CDP `Emulation.setCPUThrottlingRate` for throttling instead.
- Connector routing (`web/src/canvas/routing.ts`, contract in its module comment) is a pure search with a deterministic work budget: past `DEFAULT_ROUTE_BUDGET` expanded states it returns the marked `fallback` with `BUDGET_EXHAUSTED_REASON`, distinct from `NO_ROUTE_REASON`, so callers can tell "gave up" from "impossible". Off-main-thread routing goes through `RoutingClient` in `routingWorker.ts`, whose per-edge stale-result rule lives in `routingProtocol.ts`; `routing.perf.test.ts` measures the jittered 2,000-node worst case generated by `routingFixture.ts`. Only `orthogonal` edges are drawn through the router, via `EdgeRouteScheduler` (`edgeRoutes.ts`, one batch in flight, re-routes only edges a change can affect) and `useEdgeRoutes.ts`; routes are derived at render time and never written to the model (decision D4 a), and every other edge draws exactly as `documentIndex.ts` builds it. A connector is *pinned* when it carries `routing.waypoints` (a segment a user dragged, or ELK's bend points): an orthogonal edge with waypoints draws them directly and is not re-routed (`edgeRoutes.ts` `routable`), and "reset route" (`clearEdgeWaypoints` in `model/editor.ts`) clears them to return to derived routing. `curved` mode draws a smooth Catmull-Rom spline through the endpoints and waypoints (`web/src/canvas/curve.ts`, mirror `SmoothCurvePath` in `src/Draughtsman.Mcp/Rendering/SvgRenderer.cs`), a `<path>` not a `<polyline>`; segment/waypoint dragging is `web/src/canvas/segmentDrag.ts`, driven by `DiagramCanvas` through the same `onMoveNodes`/`moveEnd` gesture channel as a move. A selected connector shows a drag handle at each draggable middle segment (orthogonal) or waypoint plus the curve's arc-length midpoint (curved) — `segmentDrag.ts` `segmentHandles`, drawn by `SelectionOverlay.tsx` and hit-tested by `DiagramCanvas` — and a curved label sits at that arc-length midpoint (`curve.ts` `curveMidpoint`, mirrored by `SvgRenderer.CurveMidpoint`), not the polyline midpoint the straight/orthogonal labels use. An ER column port (`col:<name>`) takes its side from `ports.ts` `towardsPoint`, shared by the index, the router and the server render (mirrored by `SvgRenderer.ColumnAimX`): facing sides for side-by-side tables, but one shared side (a C bracket, no hook round the table) when the two tables overlap horizontally. `labelLayout.ts` `placeLabels` also keeps a plate off the border of its own endpoint tables (wholly inside is allowed). A node with no declared ports offers four default side ports (`defaultPorts` in `model/connect.ts`, inset onto sloped/wavy outlines), and connecting to one declares all four on the node. Two or more edges declaring the same (node, port) endpoint would otherwise leave by the identical point in the identical direction (M2 final Finding D): `ports.ts` `sharedPortOffsets` groups edges by declared endpoint and gives every sharer past the first (document order) a small tangential nudge along the node's own side (`offsetAlongSide`), applied by `documentIndex.ts`'s `edgePolyline`/`portPoint` and `edgeRoutes.ts`'s `attachment` to the fixed end a line or route starts/ends from, never to `portPosition`/`portSide` themselves (a marker, hover target or new connection still lands on the true port); a self-loop is excluded, since its exact port coincidence is `edgePolyline`'s own, separate arc-fallback mechanism. A pinned connector's waypoints never move for a move or resize (only the end segments re-attach, via `nodeBoundaryPoint`/`attachment` recomputing off current geometry every render), so `documentIndex.ts` `edgePolyline`'s `trimEnclosedWaypoints` drops any waypoint an endpoint's new bounds has grown to enclose before drawing the end segment, or that segment would cut through the enlarged shape (checklist item 10; mirrored for orthogonal, non-pinned edges by the router treating the resized node as an obstacle like any other). Edge label backgrounds (an opaque plate behind the text, the diagram theme's canvas/export background token, checklist item 11) exist in both the web canvas (`EdgeView.tsx` `EdgeLabel`) and the server SVG renderer (`SvgRenderer.cs` `AppendEdge`); `web/src/canvas/labelLayout.ts` `placeLabels` (mirrored by `SvgRenderer.PlaceEdgeLabels`) keeps two different connectors' labels from overlapping, and a label off every node's box other than its own connector's two endpoints (M2 final Finding C: a resize could push a label to land inside the neighbouring node it ended up next to), by nudging a later one (document order) along its own middle segment away from its default midpoint until its plate clears every earlier label and every such node box, never moving an earlier label, never nudging away from its own endpoint, and never writing a position back to the model.
- Edge attachment on drawn outlines (QA-01/QA-07): a diamond (shape `diamond`, BPMN gateways) or ellipse (BPMN events) is not its box, so a connector must start on the outline. `web/src/canvas/ports.ts` (`outlineKind`, `outlineExit`, `outlinePortPoint`, `nudgedPortPoint`, the shared-port fan `SHARED_PORT_STEP`, 6 for an entity column port) is the one implementation; `documentIndex.ts` `edgePolyline` and `edgeRoutes.ts` `attachment` both call it, and `src/Draughtsman.Mcp/Rendering/EdgeAttachment.cs` mirrors it for `SvgRenderer` (which therefore fans shared ports too). An orthogonal edge with routed bends leaves its node straight towards the first bend (`aligned`). `docs/examples/decision-flow.json` is the shared fixture: `web/src/canvas/decisionOutline.test.ts` and `SvgRendererTests.Decision_flow_edges_start_on_the_diamond_outline` pin the same literal offsets, so change both together. `ROUTE_CLEARANCE` is 12, the most the dense jittered routing benchmark admits (14 and up makes its worst-case route fall back).
- Text and outline contrast: `resolveNodeStyle` turns a node's text dark or white when its fill (and no `textColor`) would make the theme's text unreadable (`theme/contrast.ts` `readableTextOn`, mirrored by `ReadableText.cs`). Chrome `--chrome-border` is the decorative hairline; control outlines use `--chrome-border-strong`, derived in `app.css` from `text` over `surface` and checked at 3:1 by `themeContrast.ts` (`CONTROL_BORDER_MIX` must match the CSS). The canvas keeps the drawing under the same screen pixels when its left edge moves (`DiagramCanvas` measure effect, `viewport.ts` `keepInPlace`), which is what stops the shape panel shifting it.
- UI work needs its atlas entry in `design/atlas/<screen>.md` first, and the PR cites it. All eight notes exist; the contract, and the Mobbin coverage gap for Lucidchart, Whimsical and FigJam, are in `design/atlas/README.md`.
- No Windows-only APIs (ADR 0001). No `System.Drawing`, no registry, `Path` APIs only.
- The Yjs shape (`sidecar/src/yjs/shape.ts`: a `Y.Map` per node and edge keyed by id under `nodes`/`edges`, `header` and `meta` maps, an `order` field per element) is a contract: the SPA must build the same shape and pin the same `yjs` version as `sidecar/package.json`, or server-side snapshots will not match the browser.
- Editor state (`web/src/model/editor.ts`, `web/src/editor/useDocumentEditor.ts`): the tab holds a Y.Doc of that shape and derives the JSON it renders and PUTs. `Y.UndoManager` tracks only `LOCAL_ORIGIN` (an agent or remote edit must never be undone locally) with an infinite capture timeout, so undo steps end only at `endUndoStep` at a gesture's end, never on Yjs's 500ms timer. Geometry gestures (drag, resize, rotate, nudge) all write through `moveNodes` and end with `moveEnd`; a discrete command (`addNode`, `deleteElements`) closes a step before and after itself. Add new edits to that hook rather than writing the Y.Doc elsewhere, and add each new edit type as a case in `web/src/editor/undoCoverage.test.ts` (checklist item 16's exact-model undo/redo audit). Render order is each element's Yjs `order` field (array position in the JSON): z-order commands write it with `setElementOrder`, never by re-inserting elements. Selection is canvas view state, never in the model. Label editing (`LabelEditor.tsx` over a node, `EdgeLabelEditor.tsx` at an edge's current route midpoint, both built on `web/src/canvas/useLabelField.ts`) is an HTML overlay whose native listeners stop propagation of every key and press, so a canvas or window shortcut never fires while it is open; a commit goes through `setLabel` (node or edge id), and an unchanged label writes nothing. A node label's line breaks have one source, `web/src/canvas/text.ts` (module comment): in a browser `sharedDomLineBreaker` lays the label out with `LABEL_TEXT_LAYOUT`, the CSS the editor's field is laid out with, and NodeView draws exactly those lines with spaces preserved; `wrapText` is only the no-layout fallback (jsdom, Node). Change label wrapping there, never in the field's own CSS. Copy, cut and paste go through the native `copy`/`cut`/`paste` events' DataTransfer (`web/src/editor/systemClipboard.ts`), never `navigator.clipboard` first: Chrome answers `readText` with a permission prompt and the promise hangs until the user responds, and the async API is missing outside a secure context, so Cmd/Ctrl+C, X and V must not be prevented on keydown. Their keys are therefore the one exception to the action registry's shortcut dispatch below: they are registered only so the palette lists them, with a shortcut that never matches (`DiagramCanvas.tsx` module comment).
- Editor safety (`design/atlas/editor-safety.md`): `saveStatus` is a comparison, not a latch - `useDocumentEditor` marks `unsaved` on any local edit, then flips back to `saved` whenever `documentsEqual` (`model/documentEquality.ts`) says the document equals the last saved base (passed through the same Yjs round trip), so undo back to the save clears it. Leaving a dirty editor is guarded in one place: `app/router.ts` `setLeaveBlocker` (installed by `editor/useLeaveGuard.ts`; the router is a hand-rolled pushState one, not react-router) holds `navigate`, back/forward and the File-menu routes, while `beforeunload` covers the tab. Back/forward are decided by the router's one `popstate` listener, which `usePathname` subscribes to and which asks the blocker before it tells the route (Chrome runs `window` listeners in registration order, so a second listener that hoped to run first never did); a held one is undone with `history.go` using the `draughtsmanIndex` stamped on every entry the app pushes. Import SQL/Mermaid take `confirmLeave={guardedLeave}` so Create asks before it creates, never after. Every new in-app exit must go through `navigate` (or `guardedLeave` before doing work first, then `navigate(path, { force: true })`), never `history.pushState`. `save()` resolves true only when the whole document is stored. Escape during a move/resize/rotate calls `onMoveCancel` -> `moveCancel`, which undoes the gesture's one open undo step and clears the redo stack, so a gesture that writes frames must not have another edit inside its open step.
- Keyboard commands are actions in one registry (`web/src/editor/actions.ts`: id, label, shortcut matcher, `enabled`, `run`), contributed by their owner (history in `useDocumentEditor`, selection/viewport/label commands via `DiagramCanvasHandle.actions`, tools/grid/align/save in `DocumentViewer`). Each owner's keydown runs them through `dispatchShortcut`, and the Cmd/Ctrl+K palette (`editor/CommandPalette.tsx`) and the top bar menu (`editor/EditorMenu.tsx`, registry groups folded into File/Edit/View/Arrange/Help by `editor/menus.ts`) list the same records, so add a new shortcut as an action there, never as a bare keydown branch, or neither will show it (checklist item 28: every canvas action needs a visible menu entry). CSRF (`CsrfMiddleware`, ASP.NET Core's `IAntiforgery`) has one sharp edge worth remembering before touching it: a request token embeds the caller's claims identity and `GetAndStoreTokens` caches its result for the rest of the request the first time it's called, so the pair can only be (re)issued once, from inside the endpoint that just changed who `HttpContext.User` is (`AuthEndpoints.StartSession`/`Logout`) - never unconditionally in the middleware, which would bake in the identity the caller had a moment before signing in or out (the one exception is a refused, session-authenticated mutating request, which reissues the pair in its own 403 with `X-Draughtsman-Csrf: reissued`, and `documentClient.putDocument` retries once on it, so a tab that outlived an upgrade loses no edit). A 2026-09-29 security review  hardened several sharp edges further: `AuditEntry.ActorUserId` is always the authenticated caller's own row id (never null), fed through `IActorContext` so the transport-agnostic `DraughtsmanTools` learns it without depending on ASP.NET Core - `HttpActorContext` over HTTP, `NullActorContext` over stdio - and an `agent:<name>/<model>` header/argument only annotates that owner, never replaces it. First-run is gated by a one-time setup code (`SetupCodeGate`, printed to the log at startup, required in the request body) and its check-and-create is one atomic call (`IUserStore.TryCreateFirstUser`, a serializable transaction) rather than a check then a write, closing a real concurrent-first-run race proven against both providers. The same atomic shape (`TryDemoteAdmin`/`TryDeactivateAdmin`) stops a change from ever leaving zero active admins - a plain count-then-write left open exactly the race where two different admins each demote or deactivate the *other*, neither caught by the pre-existing self-only guard, and a concurrent test reproduces it reliably without the transaction. `AuthPolicies.CookieOnly`/`CookieAdminOnly` exist because an API token carries its owner's role (`PrincipalFactory.ForUser`), so plain role checks alone would let a token minted by an admin manage accounts or mint further tokens through itself - `/api/users` and `POST /api/tokens` require a cookie session outright, and revoking a token other than your own additionally requires a cookie-authenticated admin (a token can still revoke itself). `FailedSignInThrottle` keys the account-level bucket on the (email, IP) pair, not email alone, to stop an attacker locking a real user out of their own account from elsewhere; the pair bucket clears on success but the separate per-IP bucket deliberately never does, and every attempt is recorded before the (now dummy-hash-backed on a missing/inactive account, for constant-time failure) Argon2 verify runs rather than after, closing a burst-of-concurrent-guesses gap. `server.knownProxies`/`UseForwardedHeaders` and `server.forceHttps` (a scheme-override middleware run before anything reads `Request.IsHttps`, so every Secure-cookie decision - ours and the framework's own antiforgery cookie - and `UseHsts()` fall out of that one flag) are both config, defaulting closed. `GET /api/auth/status` reissues the XSRF cookie for any authenticated caller, since it isn't tied to the session cookie's 30-day lifetime and the SPA calls this endpoint on every load; data-protection keys persist under the data folder so a restart doesn't invalidate every outstanding one.
