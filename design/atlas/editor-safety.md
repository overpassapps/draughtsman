# Editor safety: leaving with unsaved edits, and cancelling a drag

## Screen
Two small behaviours of the editor shell (`design/atlas/editor-shell.md`), not a new screen: the question the editor asks when leaving would throw unsaved edits away (`web/src/editor/LeaveDialog.tsx`, `useLeaveGuard.ts`), and Escape cancelling a drag in progress (`web/src/canvas/DiagramCanvas.tsx`). Found by a real-browser QA pass (`data/qa-new-editor-features/report.md`, items B0, 2 and 3). Key pattern questions: what does the app do when a user leaves a dirty document; what does Escape do mid-drag; when does "Unsaved changes" stop being true.

This note is deliberately short and adds no visual pattern: the dialog reuses the Import SQL dialog's chrome (`sql-import-*`, as `design/atlas/mermaid-export.md` does). No Mobbin queries were run (the task ran with the maintainer away, and the gap in `design/atlas/README.md` on Lucidchart, Whimsical and FigJam would leave the reference set unmet anyway); the rules below are the platform conventions of every editor that guards edits.

## References
In-app precedent, read in this repository:
1. `editor/ImportSqlDialog.tsx`, `editor/MermaidTextDialog.tsx` — the modal (backdrop, Tab kept inside, every key stopped from the canvas behind it).
2. `DiagramCanvas.tsx`'s Escape branches for the marquee, connector, re-attach and segment drag — the precedent that Escape abandons a gesture and the release that follows does nothing.
3. `useDocumentEditor.ts`'s ETag-guarded `save` — the one save path; the guard reuses it rather than adding one.

## What Draughtsman does
- **Leaving while unsaved** (`saveStatus` other than `saved`, on a document that saves): closing, reloading or leaving the tab gets the browser's own confirmation (`beforeunload`; a page cannot word it). Every in-app route out is held and asks: the top bar links, sign-out, the browser's back and forward, and the File menu's New diagram, Import and Back to documents. The router (`app/router.ts`) has the one hook, `setLeaveBlocker`; `navigate` goes through it, `navigate(path, { force: true })` skips it for a caller that has already asked (`guardedLeave`).
- **The question** is a modal "Unsaved changes" with **Cancel**, **Discard changes** and **Save and leave**. Escape and a click on the backdrop are Cancel, the safe answer; focus starts on Save and leave. Save and leave runs the editor's ETag-guarded save and leaves only when it stored the whole document; a refused (412) or failed save keeps the dialog open with the reason and leaves Cancel and Discard available. If the document becomes clean while the question is open (undo back to the saved state, or a save already running finishing), the navigation just goes ahead.
- **New diagram** asks before it creates anything, so Cancel leaves no empty diagram on the server. **Import SQL / Mermaid** ask after the import has made its new document (the dialog's Create is what asked to leave); Cancel leaves that document in the list, unopened.
- **Browser back and forward** cannot be vetoed, only undone: the guard puts the current page back on top of the history, asks, and on Discard or a successful save moves to the page the user asked for.
- **Autosave** (2026-09-30, below) replaced the earlier "no autosave" line that stood here.
- **When "Unsaved changes" is true.** It is a comparison, not a latch: the whole model (nodes, edges, title, theme, meta) against the last saved base version, both passed through the same Yjs round trip. A drag that ends where it began, or undo back to the last save, shows Saved again; redo past it shows Unsaved again. A sequence drop into the slot the message or participant already occupies is not an edit (a fragment stored after the last participant does not make "past the end" a move).
- **Escape mid-drag** (mouse move, resize, rotate, sequence participant reorder, sequence message reorder): the model goes back to what the press found, pointer capture is released, the insertion line and snap guides go, the release that follows does nothing, and there is no undo entry and nothing to redo. In a sequence diagram a drag writes nothing until release, so Escape only abandons it; for a move, resize or rotate the frames already written are rolled back as the one open undo step (`moveCancel`). Segment and waypoint drags are unchanged: Escape stops them and keeps what was written, as before. Selection is left as the press made it.

## Keyboard and accessibility
- The dialog is `role="dialog"` `aria-modal="true"` labelled "Unsaved changes"; a failed save is a `role="alert"` inside it. Tab cycles Cancel, Discard changes, Save and leave.
- Escape now cancels a drag for keyboard users too: the keys that end a gesture are the same as those the canvas already handled for a marquee or a connector drag.

## Amendment 2026-09-29: back and forward, and Import (QA round two)
A second real-browser pass found two exits the first fix left open (`data/qa-round-two/report.md`, BUG 1 and BUG 2). They supersede the bullets above on those two points.
- **Browser back and forward** are decided in one place, before anyone else hears of them. `app/router.ts` has a single `popstate` listener; the route state (`usePathname`) subscribes to it instead of adding its own, so it asks the guard first and only then tells the route. This replaces the guard's own capture-phase listener: Chrome runs `window` listeners in registration order whatever the capture flag, so the route state (registered when the app mounted) ran first, unmounted the editor and cleared the guard before the guard looked. A held Back or Forward is undone with `history.go` by the distance it moved (every entry the app makes carries a `draughtsmanIndex` in its state), which adds no history entry, so Cancel leaves the history exactly as it was. An entry with no index (made before the app stamped it) cannot be measured and is put right by pushing the current page over it instead. Discard or a successful save rewrites the entry to where the user was headed.
- **Import SQL / Import Mermaid ask before they create anything**, as File > New does. The dialogs take a `confirmLeave` (the editor passes `guardedLeave`): Create calls it, and the document is saved only after Save and leave or Discard changes, then opened with a forced navigation. Cancel creates nothing and returns the dialog to its ready state, its own Cancel and Escape working; a failed create does the same with the reason shown. A dialog is never left on "Creating…" without a way out. This replaces the earlier line that Import asks after it has made its document.


## Amendment 2026-09-30: autosave and stale-save recovery
The spec section 13 open decision is taken (taken by the maintainers). This supersedes the "No autosave" bullet above. Code: `editor/useDocumentEditor.ts` (timing, retry, recovery), `editor/SaveRecoveryBars.tsx`, `editor/localCopy.ts`, `editor/saveFailure.ts`, `editor/useLeaveGuard.ts`. The bars reuse the existing `viewer-conflict` strip; no new visual pattern, so no Mobbin queries.
- **When it saves.** `AUTOSAVE_DELAY_MS` (2s) after the last change, each change restarting the wait, and never more than `AUTOSAVE_MAX_WAIT_MS` (10s) after the first unsaved change, so steady editing still saves. A tab going hidden or a `pagehide` saves at once (`keepalive` where the body fits 60 KB). Only `DocumentPage` turns it on (`autosaveDelayMs`); previews, the Try page and tests have no id or no option and never save.
- **Never an older snapshot over a newer.** One save at a time; each sends the document as it is when it starts and quotes the version the last save returned. An edit made in flight leaves the status unsaved and is the next save's. Undo and redo after a save are ordinary edits: the undo history survives a save, and the state undo leaves is autosaved like any other.
- **Status.** `Saved`, `Saving…`, `Unsaved changes`, `Not saved, retrying…` (a failure that can succeed later) or `Not saved`, `Out of date` (stale). The status is a comparison against the last saved version, as before.
- **Failure.** Network errors, 408, 429, 5xx and 401 retry after 2s, 4s, 8s ... up to 30s, and at once on the browser's `online` event; 403, 404 and other 4xx stop retrying (the message says why) until the next edit or Save. The unsaved state, the error text and the leave guard stay up throughout.
- **Leave guard.** `beforeunload` still fires whenever the status is anything but `Saved` (so also while a save is failing or refused) and not once everything is saved. In-app navigation with autosave on and the document merely unsaved or saving saves first (`flush`) and goes ahead when the whole document is stored; only a failed or refused save shows the Unsaved changes question, with the reason.
- **Refused as stale (412/428).** Autosave stops, the user's document is written to `localStorage` (`draughtsman.localCopy.<id>`, several per document, at most five, following later edits), live sync stops merging so "mine" and "theirs" stay what the user was shown, and a strip asks: **Reload theirs** (the editor shows the server's version; undo history is cleared so undo cannot put "mine" back on the canvas for autosave to write over theirs; the local copy stays), **Keep mine…** (asks "Overwrite the newer version with yours?" first, then a `PUT` quoting the server's current version read at that moment; if it moved again nothing is overwritten and the question stays with the reason), **Save mine as a new document** (`POST`, title `… (my copy)`, then the server's version is shown here with an Open it link). The manual Save button is disabled while it is open.
- **Local copies** outlive the tab: on load, a copy that differs from the loaded document shows a strip (Save it as a new document / Discard copy); one equal to it is dropped. A copy is dropped automatically only by the save that stored the document it was protecting, never one from an earlier visit or one set aside by Reload theirs. `localStorage` failures are swallowed; the editor's state is still the truth.
- **Two tabs.** Live sync merges the other tab's save within a second, so the usual case needs no question; the question appears only when a save loses the race, which is exactly the stale case above.
- **Read-only.** No viewer role exists yet (`UserRole` is Admin or Editor). A document with no id saves nothing; a 403 on save stops retrying and says the server refused.

## Amendment 2026-10-01 (final usability QA: S9, S10)

- **A stale save is first tried as a merge.** After a 412/428 the editor reads the server's version and merges it into a throw-away copy of the document. If nothing clashes with what the person changed (the case the live-sync poll already merged silently), it merges for real, quotes the new version and saves once more: no "Out of date". Whether the autosave PUT or the poll reached the server first no longer decides what the person sees. A clash on something they changed, a second refusal, or a flush on leaving still asks (the three answers above).
- **Reload theirs** keeps the person's version as before and offers it (Save it as a new document / Discard copy) for the rest of that visit; the copy is marked answered, is not offered on later opens, and is deleted a week after it was kept.
- **A session ending** (401 with `X-Draughtsman-Session-Ended`) makes an open editor keep unsaved edits as a local copy before the sign-in screen replaces it; reopening the document after signing in offers them.
- **Dates** in banners and tables are `1 Oct 2026, 02:50` in the viewer's zone, the zone and seconds on hover.
